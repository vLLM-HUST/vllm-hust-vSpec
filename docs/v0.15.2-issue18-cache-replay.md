# vSpec 0.15.2 安装包的编译缓存复测

此页记录本地诊断，不把它等同于老师 issue #18 的逐参数重放，也不把不同缓存状态的两臂混算为正式加速比。测试使用独立 Python 环境中安装的 0.15.2 wheel（SHA-256 `c272ca7087bef4ca0b7da84f517ae72fa0ff14fe75571cd13b9b93e8450888d3`），两张 910B2、Qwen3.5-35B-A3B、BF16、TP=2/EP、并发上限 16、自动 KV、`FULL_DECODE_ONLY`、vSpec 动态候选档位 2/4/6/8。运行脚本、完整非路径参数与题单校验见 [issue #18 复测入口](../examples/issue18_frozen56/README.md)。

四轮均为同一冻结的 56 道 MMLU-Pro 题，Qwen chat template、14 道非计分 pilot 各最多 16 token、正式题各最多 4000 token 并自然停止；未使用额外的 `--prime-pilot16x1024`。正式输出 token/s 不包含服务启动和 pilot 时间。

| vSpec 运行口径 | 输出 token | 正式生成秒数 | 输出 token/s | 服务就绪秒数 |
| --- | ---: | ---: | ---: | ---: |
| 全新隔离编译缓存 | 157,347 | 180.01 | 874.11 | 698.23 |
| 再次全新隔离编译缓存 | 149,724 | 171.11 | 875.00 | 699.81 |
| 复制上一轮同臂缓存，第 1 次 | 151,935 | 153.34 | 990.85 | 290.04 |
| 再复制同臂缓存，第 2 次 | 154,536 | 158.35 | 975.88 | 291.91 |

四轮均 56/56 请求完成、无抢占。两轮独立冷缓存结果相差约 0.1%，证实该安装包在此环境下约 875 token/s 的首次运行**吞吐**可重复；两轮答对题数分别为 35 和 41，不能据此称逐题输出或正确率也已复现。复用缓存两轮的输出吞吐接近或超过旧归档优化代码曾记录的 950.04–969.27 token/s；但旧轮使用固定 KV 和五个热静态形状，本页用自动 KV 和单热形状 70，故只能说**恢复了该负载上的吞吐量级**，不能宣称逐参数、逐 token 复刻。复用缓存轮中仍运行 14 道短 pilot，但不额外运行长生成 pilot。它们是热编译缓存口径，不是首次安装后的全新缓存成绩。

冷缓存轮与复用轮使用同一已安装 wheel、模型、题单和脚本；56 道题的 ID、提示词 SHA-256 和长度也与旧归档轮一致。两轮复用成绩相对首个冷缓存轮分别高约 13.4% 和 11.6%，说明编译缓存状态是这次吞吐落差的重要因素；不同轮的自然输出长度与调度仍有变化，单靠这些数值不能证明缓存是唯一因素。匹配的原生 MTP4 冷缓存轮为 802.67 token/s；两次冷缓存 vSpec 分别约为其 1.089 倍和 1.090 倍，尚未达到 1.1 倍。当前证据也**不能**把 990.85 或 975.88 与冷缓存原生结果直接相除称为正式配对加速比。若要建立热缓存口径倍率，需让原生臂采用匹配的缓存口径另做一次配对测试。

复用方法：对第一次运行的私有结果目录使用 `--reuse-cache-from <该目录>`，并把 `--output` 指向全新的目录。脚本复制缓存、重定位 Triton 编译产物引用，并在 `receipt.json` 中记录来源。仅在相同模型、后端、算子、设备架构和引擎参数下复用；不要把别人的缓存文件或不同软件版本的缓存当成可移植安装资产。缓存并不包含题目答案或运行中的 KV，但会占用磁盘。此行为不改变 0.15.2 wheel 内容，也不意味着安装插件会预先生成模型相关编译缓存。

冷启动优化另行验收。本页两次隔离缓存轮的服务就绪时间分别为 698.23 和 699.81 秒，均低于先前 20 分钟目标；复用轮更短，但只能归入热缓存启动，不能替代首次启动测试。

## 长预热单变量诊断（扩展协议）

保持已安装 wheel、冻结题单、Qwen chat template、自动 KV、环境配置及全新隔离缓存不变，仅在原有 14 题×16 token pilot 后增加 `--prime-pilot16x1024`。服务就绪 691.07 秒，短 pilot 29.69 秒，额外 16 题 pilot 共生成 15,693 token、耗时 33.10 秒；正式 56 题输出 156,789 token / 163.54 秒，即 **958.73 token/s**，无抢占。答对 39/56；此小样本正确数不用于全量质量结论。

两轮仅短预热的冷缓存测试在正式阶段分别新增 5 个相同类型的 Triton 二进制算子：3 个 GDN refresh 变体、1 个 Mamba 后处理和 1 个 batch memcpy。加长预热轮把其中 3 个提前到了额外 pilot 阶段，正式阶段仍新增 2 个 GDN refresh 变体。吞吐相对两轮短预热的约 875 token/s 提高约 9.6%，回到旧归档的 950–969 token/s 量级。这支持“短 pilot 未覆盖首次编译”是落差的重要原因，但不能断言是唯一原因；额外 pilot 也可能影响在线档位状态和自然输出长度。

**该长预热不是 issue #18 原始冻结协议。** 首次安装后若要重现上述长预热口径，须显式加参数并把启动、短 pilot、额外 pilot 与正式计时分别报告；不能把它写成原始 14 题短预热的冷缓存成绩，更不能与短预热原生臂直接相除。

同一长预热口径下补测的原生 MTP4 为 151,800 输出 token / 182.98 秒，即 829.61 token/s，服务就绪 543.60 秒；两臂均 56/56 完成、无抢占，答对均为 39/56。两份回执的题单、提示词选项、引擎配置与环境配置哈希相同，且都未复用编译缓存。按正式输出 token/s 配对，vSpec / 原生 MTP4 = **1.156×**。此倍率仅适用于双方均执行额外长 pilot 的扩展协议，不代表原始仅短 pilot 的冷缓存加速比；后者现有数据约为 1.09×。

## 仅预置 Triton 内核的因果诊断

为区分正式计时中的 Triton 即时编译与其他缓存效应，又做了一轮仅复制前述冷轮中 `gdn_gid123_full_stable_refresh`、`postprocess_mamba_fused_kernel`、`batch_memcpy_kernel` 三类编译产物的诊断。图捕获、ACL、静态内核等缓存仍为全新，题单、自动 KV、14 题×16 token 短 pilot 和正式计时规则不变；回执标注 `seed_triton_kernels_from`，**不是全新安装复现成绩**。

这轮服务就绪 716.60 秒，短 pilot 23.26 秒；正式 56 题输出 155,863 token / 156.91 秒，即 **993.34 token/s**，正式期间新增 Triton 二进制数为 0。相对两次全新短 pilot 冷轮约 875 token/s，增加约 13.5%；正式耗时差也与前述五个新变体的编译时间量级相符。因此此环境下落差的主因已收敛到**短 pilot 未覆盖正式阶段才首次调用的 Triton 特化变体**，尤其是动态档位的 GDN 宽度、单请求尾部 Mamba 后处理和块复制。仍不能把预置旧产物当作可移植解决办法；下一步需在安装包中于正式计时前自行完成这些编译，并在独立空缓存下验收。

## 运行时预编译的空缓存验证（尚非新包安装验证）

后端新增可选开关 `VLLM_ASCEND_Q35_GDN_PRECOMPILE_WIDTHS=1`。当 Qwen3.5/vSpec 首次进入符合条件的 GDN 解码路径时，使用当前机器上已分配的真实张量参数，调用 Triton 的 `warmup` 编译 2/4/6/8 档位对应的 GDN 宽度及单请求尾部 Mamba/块复制特化；`warmup` 只编译，不执行模型计算，也不读取题目答案。测试环境配置已显式设置该开关，原有的 14 道短 pilot 题和正式 56 题均不变。

在已安装 0.15.2 环境中临时替换后端源码、并使用**全新隔离编译缓存**测试，服务就绪 706.78 秒，14 题短 pilot 生成 224 token、耗时 47.76 秒；正式 56 题输出 155,855 token / 159.18 秒，即 **979.11 token/s**，56/56 完成、无抢占。短 pilot 后到正式结束，新增 Triton `.npubin` 文件为 **0**。它比两次未启用预编译的空缓存短 pilot 轮约 875 token/s 高约 11.9%，与只预置三类内核的诊断轮 993.34 token/s 相差约 1.4%。这支持“正式计时内的迟到编译”是此前约 100 token/s 落差的主要原因；自然停止下的输出长度仍会变化，不宜把单轮差值解释为纯编译耗时。

这两轮验证的是**实现方向**，当时还不是从新 wheel 安装后的复现；后文另列新 wheel 安装与空缓存复测。该开关目前只在 issue #18 复测配置中启用；它按模型、设备和运行形状准备算子，不针对 MMLU-Pro 题目内容。

相同配置的第二次全新隔离缓存轮也完成 56/56、无抢占：服务就绪 719.51 秒，短 pilot 224 token / 47.89 秒，正式 152,569 token / 158.25 秒，即 **964.10 token/s**；正式阶段新增 Triton `.npubin` 仍为 0，答对同为 38/56。这轮在后端 wheel 的 CPU 编译任务并行运行时测得，不能据此推断稳定态 979→964 的差异完全由随机波动或代码变化造成。两轮共同说明预编译覆盖在空缓存下可重复，且吞吐回到旧归档的 950–969 token/s 范围。

## 新 wheel 安装后的空缓存复测

把上述后端改动打入新的 0.15.2 插件 wheel（SHA-256 `03cd24af975a09d42109b2bc6ca3f1aa2d9a52ddff17cb5b2e2f46301cd6ba05`），并从相同源码生成新的 Ascend 后端 wheel（SHA-256 `41bcd108145cc133aba4ee5cc34accd7937467c209329829f06a8ac09eb2e99c`）。在新的 Python 虚拟环境中安装这两个 wheel，使用独立空编译缓存、自动 KV、相同的 Qwen chat template、14 题×16 token 短 pilot 和正式 56 题；未复制旧缓存，也未增加长 pilot。

这轮服务就绪 686.01 秒，短 pilot 224 token / 48.15 秒；正式输出 **152,660 token / 158.36 秒 = 964.01 token/s**，56/56 完成、无抢占。正式阶段新增 Triton `.npubin` 为 0。该结果与上面手工替换后端的两次空缓存轮处于同一量级，说明预编译改动已进入插件及后端安装产物，并在新安装环境里恢复了旧归档 950–969 token/s 的吞吐量级；它不是预置旧编译缓存得到的成绩。

随后用同一新环境、题单、chat template、自动 KV、短 pilot 和独立空缓存运行原生 MTP4：服务就绪 540.69 秒，短 pilot 224 token / 22.01 秒，正式输出 **147,946 token / 184.35 秒 = 802.53 token/s**，56/56 完成、无抢占。两臂回执的题单、引擎配置和环境配置哈希一致；按正式输出吞吐配对，vSpec / 原生 MTP4 = **1.201×**。两组自然停止输出 token 总数不同，不能把该倍率解释为每个请求等量输出下的纯算子加速；本轮也不是老师原始启动包的逐参数复刻。vSpec 冷启动比原生多约 145 秒，虽然两者均低于 20 分钟目标；vSpec 短 pilot 因预编译多约 26 秒。把服务就绪、pilot 和正式生成简单相加（不含题目准备/评分），首次运行约为 vSpec 892.51 秒、原生 747.06 秒；**正式吞吐提高并不代表首次整轮更快**，后续仍需优化冷启动。

验收边界：新环境的基础依赖沿用前一虚拟环境的锁定版本；未改动的本机原生算子产物和安装器生成的运行路径沿用此前已验证的产物。本轮重新安装了插件和 Ascend 后端 wheel，**尚不能称作从空机器执行完整安装器的一键验收**，也不能保证不同机器上得到完全相同的吞吐。预编译把编译时间移入短 pilot，首次运行的端到端时间必须另计服务启动和 pilot。

## 完整安装入口与重新构建算子的复测

随后在同一个新虚拟环境中，以该插件 wheel 调用仓库 `install.sh`，重新构建并安装 Ascend 后端与全部原生算子，逐项通过双卡组件校验；安装器退出码为 0，写出新的 `runtime.env` 和 `installed.json`。运行中的 worker 环境确认 `conv-stride`、`gamma6-rgdr`、`gamma8-rgdr` 等路径指向这次新建的组件目录，不沿用前一轮的原生算子产物。安装器未设置物理卡绑定；基础 Python 依赖、系统驱动、CANN、模型和数据集仍是预先准备的外部条件，因此这不是“空机器直接 pip install 即可运行”的保证。

使用完整安装产物和独立空编译缓存、相同题单与配置重新运行 vSpec：服务就绪 **696.57 秒**，短 pilot 224 token / 49.12 秒；正式 56 题输出 **154,875 token / 165.43 秒 = 936.19 token/s**，56/56 完成、无抢占，正式阶段新增 Triton `.npubin` 为 0。相对上面仍沿用旧原生算子产物的 964.01 token/s，观察吞吐低约 2.9%；两轮自然输出长度也不同，单凭一次重跑不能归因于算子重建。

随后在同一完整安装环境中用独立空编译缓存配对测原生 MTP4：服务就绪 **563.97 秒**，短 pilot 224 token / 20.26 秒；正式 56 题输出 **149,944 token / 204.91 秒 = 731.77 token/s**，56/56 完成、无抢占。两臂题单、引擎配置、环境配置哈希一致，正式吞吐倍率为 **1.279×**。但原生本轮比安装前的 802.53 token/s 低约 8.8%，正式阶段还新编译 1 个 Triton 二进制；相同计数也见于安装前原生轮，故不能仅用此解释落差。该原生波动尚待复核，不应只引用较低基线而回避 vSpec 自身 2.9% 的下降。把启动、pilot 和正式生成相加（不含题目准备/评分），首次整轮约为 vSpec 911.12 秒、原生 789.14 秒，vSpec 仍慢约 122 秒；**输出吞吐加速不等于首次整轮加速**。

## 2026-11-11 新环境完整安装再验

另建 Python 3.11 虚拟环境，在预先备好的同版本基础依赖、系统驱动和 CANN 上，从 0.15.2 插件 wheel（SHA-256 `03cd24af975a09d42109b2bc6ca3f1aa2d9a52ddff17cb5b2e2f46301cd6ba05`）运行仓库 `install.sh`：后端从冻结源码重新构建，所有原生算子重新构建并逐项通过双卡校验，安装器退出码为 0。模型、数据集和基础依赖不是安装包自动下载的内容；这验证新虚拟环境的完整安装路径，**不等于跨机器或空 OS 安装保证**。

随后在独立空编译缓存中，以自动 KV、Qwen chat template、14 题×16 token 短 pilot、56 题正式负载复测 vSpec，未执行额外长 pilot，也未复用上轮缓存。服务就绪 **700.08 秒**，短 pilot 224 token / **47.54 秒**；正式题输出 **149,777 token / 153.45 秒 = 976.05 token/s**，56/56 完成、零抢占，答对 39/56，22 题达到输出上限。该吞吐比上一次完整安装单臂的 936.19 token/s 高约 4.3%，没有观察到性能下滑；首次启动低于 20 分钟，但启动与 pilot 均不在正式吞吐分母中。本轮未在此新环境运行匹配的原生 MTP4，因此**不能据此计算新一轮配对加速比**。可复算的脚本、自动 KV 配置及脱敏聚合结果分别见[复现入口](../examples/issue18_frozen56/README.md)和[结果 JSON](../examples/issue18_frozen56/result-20261111-new-env-vspec-auto-kv.json)。
