# vSpec v0.15.1: preparing a matching Ascend environment

This guide covers the packaged experimental Qwen3.5 execution components. Keep
build directories, validation proofs, prompts, manifests, logs and results in a
private work area. The plugin package contains source and validation commands;
it does not install a system driver or CANN, download a model, or ship task data.
Component success is not a model-level speed or quality result.

The [local retest profile and aggregate observations](v0.15.1-local-retest.md)
record the exact benchmark settings and separate a four-arm local series from
later clean-install diagnostic runs. Raw cases, prompts and proofs remain
private; the published hashes alone do not reconstruct the historical case
selection.

Cold server startup is a known performance limitation of this experimental
profile: first-time compilation and decode graph capture can take tens of
minutes. Measure startup separately from request-window output throughput;
do not present the latter as an end-to-end time including startup. Reducing
the cold-start cost is follow-up work, and a reused compile cache must be
recorded explicitly when comparing runs.

## Host and Python stack

The currently targeted stack is ARM64, two allocated Ascend 910B2 devices,
Python 3.11, CANN 9.1, PyTorch 2.13.0, torch-npu 2.13.0rc1 and triton-ascend
3.6.0. Use the device driver and Python wheels compatible with the same CANN
installation. Use the same pinned Python stack for build and run within each
arm; the native and dynamic arms may use separate clean environments. The source
revisions are:

| Source | Revision |
|---|---|
| vLLM-HUST | `762f85b311fbab0bcf8921dd216f5093cd58b9b8` |
| vLLM-Ascend-HUST, before the packaged patch | `4e57439e58ed3d78e675f9fd7b4614fb183c5394` |
| vSpec plugin | the v0.15.1 release commit being evaluated |

The Qwen3.5-35B-A3B target checkpoint must include its MTP head, tokenizer and
chat template. The model and public datasets can be mounted read-only. Set up
the virtual environment and CANN SDK using the host vendor's installation
instructions before running the following commands. `<...>` denotes a path
chosen by the operator, never a path supplied by this package.

## Install the matched backend, plugin and operators

Install the pinned vLLM source, PyTorch, torch-npu, triton-ascend and their
compatible dependencies into the selected Python 3.11 environment. Confirm
the selected interpreter with `python -m pip show vllm torch torch-npu
triton-ascend`. Run the supplied installer with two idle allocated NPUs. It
installs the plugin, builds and installs the matched backend and its custom OPP,
builds the packaged operators, validates them on the actual devices and writes
`runtime.env` with the resulting private paths.

The pinned Ascend checkout must also contain its three offline CANN build
archives under `csrc/third_party/pkg/`: `abseil-cpp-20230802.1.tar.gz`,
`protobuf-25.1.tar.gz`, and `include.zip`. They are not tracked by the base
Git commit. The installer verifies their SHA-256 digests before copying them
into the private backend build tree; it fails early if an archive is missing
or different. On a large host, set `MAX_JOBS` to a practical build parallelism
to avoid launching one compiler per visible CPU.

Run the installer with:

```bash
source <CANN_ROOT>/set_env.sh
./install.sh --python <VENV_PYTHON> --wheel <VSPEC_WHEEL> \
  --ascend-source <ASCEND_GIT_CHECKOUT> --vllm-source <PINNED_VLLM_SOURCE> \
  --cann-root <CANN_ROOT> --model-dir <MODEL_DIR> \
  --private-dir <NEW_PRIVATE_INSTALL_DIR>
source <NEW_PRIVATE_INSTALL_DIR>/runtime.env
```

Source the CANN environment again in every new shell used to launch a model,
before sourcing `runtime.env`. In particular, the runtime linker must be able
to find `<CANN_ROOT>/lib64/libhccl.so`. The generated `runtime.env` supplies
the private vSpec component paths; it does not replace the vendor driver/CANN
environment. The backend wrapper prepends its custom-operator library path to
the existing CANN library path.

Use `--dry-run` to check the complete command plan without writing files.
`<NEW_PRIVATE_INSTALL_DIR>` must not exist yet; the installer leaves failed
builds in that directory for diagnosis and requires a fresh directory to retry.
The model is read-only and may live in shared storage. Build products and
proofs remain under the private directory. The driver, CANN SDK and pinned
Python dependencies are prerequisites; a standard `pip install` of a wheel
cannot execute device-specific compilation as a post-install hook. Users with
only the wheel can first install it with pip, then call
`vllm-hust-vspec-install-runtime` with the source/CANN/model/private path flags;
the wheel path need not be passed again. The repository's
`install.sh` performs both operations in one command.

For manual diagnosis, the installer executes the following backend steps with
the selected interpreter:

```bash
python -m pip install --no-deps <VSPEC_WHEEL>
vllm-hust-vspec-prepare-backend \
  --source <ASCEND_GIT_CHECKOUT> --destination <NEW_BACKEND_SOURCE_DIR>
ASCEND_HOME_PATH=<CANN_ROOT> python -m pip wheel --no-build-isolation --no-deps \
  --wheel-dir <PRIVATE_WHEEL_DIR> <NEW_BACKEND_SOURCE_DIR>
python -m pip install --no-deps <BUILT_ASCEND_WHEEL>
python -m pip show vllm-ascend vllm-hust-vspec
```

`--no-build-isolation` makes the backend build use the selected environment's
PyTorch and torch-npu. The backend wheel contains its CANN custom operators;
the plugin wheel contains the backend patch and the vSpec component sources.
Use the directory *containing* `vllm_ascend` as `<VENV_SITE_PACKAGES>` in the
commands below. Do not point `--backend-package` at `vllm_ascend` itself.
After installation, this read-only check also verifies that the wrapper and
child interpreter use the selected backend:

```bash
vllm-hust-vspec-run-with-backend --backend-package <VENV_SITE_PACKAGES> \
  -- <VENV_PYTHON> -c 'import vllm_ascend; print(vllm_ascend.__file__)'
```

The wrapper sets `ASCEND_CUSTOM_OPP_PATH` and `LD_LIBRARY_PATH` from the
installed backend. A CANN-generated `set_env.bash` in a relocated wheel may
still refer to its old build directory and must not select that old directory.

For Qwen3.5 with its single MTP head, **both** the native MTP4 and dynamic
vSpec server commands must use the same opt-in KV/Mamba compatibility bridge:

```bash
vllm-hust-vspec-run-with-backend --backend-package <VENV_SITE_PACKAGES> \
  --qwen35-mtp-compat -- <VENV_PYTHON> <SERVER_ENTRYPOINT_AND_IDENTICAL_ARGS>
```

The option prepends the packaged `qwen35_mtp_compat` directory to the child
process `PYTHONPATH` and sets `QWEN35_MTP_COMPAT=1`. Its `sitecustomize.py`
loads before vLLM plugin registration, including in spawned workers. It
imports only standalone Qwen3.5 compatibility modules, not `vllm_hust_vspec`;
the native arm does not need the vSpec plugin enabled. The KV bridge admits
only the expected target/MTP layer-zero pair and preserves the generic guard
for other duplicate indices. The Mamba bridge shares idempotence markers
with the dynamic plugin. Do not set the flag for other models, change its
loading order, or enable it for only one arm. Removing the option leaves this
startup bridge inactive. This wrapper is an environment and command launcher,
not a packaged model-specific server/evaluation harness.

## Build and validate components

Use a fresh private directory for each build or proof. Keep the two NPUs idle
while a component validator is running. Every validation command uses the
installed plugin, the selected backend, and its locally built source. The
reference dependencies below are ordered; run each dependent row only after
its predecessor passes. `--cann-root` is the installed SDK root containing
AscendC CMake support.

| Component | Build command | Validation command |
|---|---|---|
| Convolution reference | `vllm-hust-vspec-build-operator --operator conv-reference --cann-root <CANN_ROOT> --destination <CONV_REF>` | `vllm-hust-vspec-validate-conv --component reference --component-dir <CONV_REF> --backend-package <VENV_SITE_PACKAGES>` |
| Convolution stride | `vllm-hust-vspec-build-operator --operator conv-stride --cann-root <CANN_ROOT> --destination <CONV_STRIDE>` | `vllm-hust-vspec-validate-conv --component stride --component-dir <CONV_STRIDE> --backend-package <VENV_SITE_PACKAGES> --reference-dir <CONV_REF>` |
| Convolution edge | `vllm-hust-vspec-build-operator --operator conv-edge --cann-root <CANN_ROOT> --destination <CONV_EDGE>` | `vllm-hust-vspec-validate-conv --component edge --component-dir <CONV_EDGE> --backend-package <VENV_SITE_PACKAGES>` |
| Gamma-six tail convolution | `vllm-hust-vspec-build-operator --operator gamma6-tail --cann-root <CANN_ROOT> --destination <G6_TAIL>` | `vllm-hust-vspec-validate-tail-conv --component-dir <G6_TAIL> --backend-package <VENV_SITE_PACKAGES>` |
| Gamma-six recurrent reference | `vllm-hust-vspec-build-operator --operator gamma6-rgdr-reference --cann-root <CANN_ROOT> --destination <G6_REF>` | `vllm-hust-vspec-validate-rgdr --component gamma6-reference --component-dir <G6_REF> --backend-package <VENV_SITE_PACKAGES>` |
| Gamma-six packed reference | `vllm-hust-vspec-build-operator --operator gamma6-rgdr-packed-reference --cann-root <CANN_ROOT> --destination <G6_PACKED_REF>` | `vllm-hust-vspec-validate-rgdr --component gamma6-packed-reference --component-dir <G6_PACKED_REF> --backend-package <VENV_SITE_PACKAGES> --reference-dir <G6_REF>` |
| Gamma-six recurrent variant | `vllm-hust-vspec-build-operator --operator gamma6-rgdr --cann-root <CANN_ROOT> --destination <G6_RGDR>` | `vllm-hust-vspec-validate-rgdr --component gamma6-packed --component-dir <G6_RGDR> --backend-package <VENV_SITE_PACKAGES> --reference-dir <G6_REF> --prior-dir <G6_PACKED_REF>` |
| Gamma-eight recurrent variant | `vllm-hust-vspec-build-operator --operator gamma8-rgdr --cann-root <CANN_ROOT> --destination <G8_RGDR>` | `vllm-hust-vspec-validate-rgdr --component gamma8 --component-dir <G8_RGDR> --backend-package <VENV_SITE_PACKAGES>` |
| RGDR state pipeline | `vllm-hust-vspec-build-operator --operator rgdr-state-pipeline --cann-root <CANN_ROOT> --destination <RGDR_PIPELINE>` | `vllm-hust-vspec-validate-rgdr-state-pipeline --component-dir <RGDR_PIPELINE> --backend-package <VENV_SITE_PACKAGES>` |
| FIA host adapter | `vllm-hust-vspec-build-operator --operator fia-host --cann-root <CANN_ROOT> --destination <FIA_HOST>` | `vllm-hust-vspec-validate-fia-host --directory <FIA_HOST>` |

The remaining components have no separate CMake build. Validate them with
fresh private output directories:

```bash
vllm-hust-vspec-validate-gdn-input --width 6 --backend <VENV_SITE_PACKAGES> \
  --vllm-source <PINNED_VLLM_SOURCE> --destination <G6_INPUT>
vllm-hust-vspec-validate-gdn-input --width 8 --backend <VENV_SITE_PACKAGES> \
  --vllm-source <PINNED_VLLM_SOURCE> --destination <G8_INPUT>
vllm-hust-vspec-validate-mask --backend <VENV_SITE_PACKAGES> --destination <G6_MASK>
vllm-hust-vspec-validate-prefix-clip --backend <VENV_SITE_PACKAGES> \
  --destination <PREFIX_CLIP>
vllm-hust-vspec-validate-two-bank --model <MODEL_DIR> --destination <TWO_BANK>
vllm-hust-vspec-validate-inplace-head --model <MODEL_DIR> --destination <INPLACE_HEAD>
```

The default-off `HUST_ISSUE18_Q35_NATIVE_CONV_TILE` direct-stride experiment is
outside this reproduction profile. Its `VSPEC_NATIVE_CONV_TILE_DIR` requires a
different kernel and proof; `<CONV_REF>` does not supply them, and v0.15.1 does
not package that kernel's build source or a proof-generation entry point.

Proofs are bound to the physical NPU allocation. Rebuilds or a changed device
assignment require fresh proofs. Keep every artifact for later source-hash and
numerical inspection. An installed plugin alone does not select the
experimental worker; the serving application must explicitly load its worker
and preserve the same cache, graph, precision and request settings for native
and vSpec runs. The package includes an opt-in evaluation endpoint, standalone
native worker, dynamic worker, and a paired three-dataset launcher in
[`examples/qwen35_three_datasets`](../examples/qwen35_three_datasets/README.md).
Use the pinned vLLM endpoint plugin interface and activate `vspec_eval`
explicitly for both arms; the native child must not import the vSpec strategy.
The example does not ship the model, task assets, judge service, system driver,
or compiled operator proofs. Component readiness alone is not independent
reproduction of the reported benchmark.

## Model-level acceptance before publishing

Test the native MTP4 and dynamic vSpec arms sequentially on the same allocated
NPUs. Use identical checkpoint, BF16 precision, task manifest, prompt template,
output limit, concurrency, cache policy, graph settings and quality scorer.
Record the backend and plugin commit, model and task manifest hashes, answer
files, token counts, timed intervals and unresolved-scoring counts in private
evidence. MMLU-Pro and HLE-Verified require at least 200 questions each;
FrontierScience requires both tracks, at least 160 tasks in total, and complete
coverage of the selected split. The release gate expects
each dataset to pass throughput of at least 1.10× native MTP4 and the agreed
two-percentage-point quality tolerance.

When an independent reviewer has checked the private evidence, produce a
private JSON receipt with this shape. Each digest identifies an actual private
artifact; placeholders shown here must be replaced. The receipt contains pass
decisions and hashes, not the raw configuration, prompts or results:

```json
{
  "schema_version": 1,
  "plugin_version": "0.15.1",
  "git_commit": "<40-character release commit>",
  "backend_commit": "4e57439e58ed3d78e675f9fd7b4614fb183c5394",
  "evidence_manifest_sha256": "<SHA-256 of private evidence manifest>",
  "datasets": {
    "MMLU-Pro": {"sample_count": 200, "full_split": false, "throughput_ge_1_10": true, "quality_within_2pp": true, "evidence_sha256": "<SHA-256>"},
    "HLE-Verified": {"sample_count": 200, "full_split": false, "throughput_ge_1_10": true, "quality_within_2pp": true, "evidence_sha256": "<SHA-256>"},
    "FrontierScience": {"sample_count": 160, "full_split": true, "throughput_ge_1_10": true, "quality_within_2pp": true, "evidence_sha256": "<SHA-256>"}
  }
}
```

The reviewed receipt must record the actual complete-split count. Check locally with
`python scripts/verify_model_acceptance.py --receipt <PRIVATE_RECEIPT> --commit <RELEASE_COMMIT>`.
For GitHub release automation, configure the protected `pypi` environment
secret `VSPEC_MODEL_ACCEPTANCE_RECEIPT` with the reviewed JSON. `release.sh
publish` also accepts `VSPEC_MODEL_ACCEPTANCE_RECEIPT_FILE` pointing to the
private file. No receipt, wrong commit, missing dataset or failed gate means
publication stops. The workflow prints only the receipt SHA-256 for auditing.
